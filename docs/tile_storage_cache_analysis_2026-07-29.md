# 分块存储 Cache 性能原理与内存开销分析

**日期**: 2026-07-29
**状态**: 设计讨论
**前设文档**: [[panel_data_storage_design_2026-07-29]]

---

## 一、问题重述

Panel 数据（股票 × 日期）需要同时支持两种访问方向：

| 方向 | 模式 | 例子 |
|------|------|------|
| 时序 | 固定股票，沿日期遍历 | SMA, 动量, 波动率 |
| 截面 | 固定日期，沿股票遍历 | rank, zscore, 行业中性化 |

两种访问方向对应**互斥的内存布局偏好**——时序要行优先（stride=1），截面要列优先（也是 stride=1）。分块（tile）存储通过在中间地带折中，让两个方向都接近 cache 最优。本文从 CPU cache 微架构层面解释其原理，并量化内存开销。

---

## 二、当前布局的截面瓶颈

### 当前 MarketData 布局

```
Stock_A CLOSE: [D1, D2, D3, ..., D1000]     ← 连续 8KB
Stock_B CLOSE: [D1, D2, D3, ..., D1000]     ← 另一块堆内存
Stock_C CLOSE: [D1, D2, D3, ..., D1000]
...
Stock_1000 CLOSE: [D1, D2, D3, ..., D1000]
```

1000 只股票 × 1000 个日期 × 每只股票独立分配 = 1000 次 SQL 类型的堆分配，散布在地址空间各处。

### 截面访问的 cache 行为

在日期 D_k 做全市场 rank（截面访问），需要取：

```cpp
Stock_A.CLOSE[D_k]  // 偏移 = k×8, 但在 S_A 的内存区域
Stock_B.CLOSE[D_k]  // 偏移 = k×8, 但在 S_B 的内存区域（完全不同的页）
Stock_C.CLOSE[D_k]
...
```

每次访问的微观过程：

```
访问 S_A.CLOSE[D_k]:
  → TLB lookup: 可能 miss（跨页边界）
  → L1 load: miss
  → L2 load: miss
  → L3 load: miss
  → DRAM fetch: 加载包含该值的 64 字节 cache line
  → 64 字节中只用了 8 字节（1 个 double），利用率 12.5%

访问 S_B.CLOSE[D_k]:
  → 同上，完全不同的物理页，新一轮 cache miss

...重复 1000 次
```

### 量化代价

| 指标 | 值 | 说明 |
|------|----|------|
| Cache line 大小 | 64 字节 | x86-64 标准 |
| 每次截面访问的有效数据 | 8 字节（1 double） | 利用率 12.5% |
| 1000 只股票的截面 | ~1000 次 cache miss | 每只股票的数据在独立堆块中 |
| 每次 DRAM 访问延迟 | ~200 cycles | DDR5-5600 ≈ 80-100ns, CPU @ 3.5GHz ≈ 0.28ns/cycle |
| 总等待时间 | ~200,000 cycles | 仅内存等待，不含计算 |

**带宽浪费**: 从内存搬了 64KB（1000 × 64B cache line），只用了 8KB（1000 × 8B），浪费 87.5%。

此外还有：
- **TLB miss**：1000 次访问可能跨越 1000 个不同的 4KB 页
- **硬件预取器失效**：访问模式是 `addr(S_A+D_k), addr(S_B+D_k), ...`，间隔不规律，预取器无法预测下一个地址

## 三、分块存储的 cache 行为

### 布局方案

```
Tile (64 stocks × 64 dates), 共 8 个字段:

       D1     D2     ...  D64
S_1    v[0]   v[1]   ...  v[63]
S_2    v[64]  v[65]  ...  v[127]
...
S_64   v[...] v[...] ...  v[4095]

内存布局（行优先平铺，单字段）：
[S1_D1, S1_D2, ..., S1_D64, S2_D1, S2_D2, ..., S64_D64]
 ^^^^^ 连续 512 字节（64 doubles × 8B）^^^^^^^^^
```

一个 tile 内单字段的大小：64 × 64 × 8 = **32KB**。

### tile 大小的选择依据

| 约束 | 值 | 含义 |
|------|----|------|
| L1 data cache | 32KB-48KB (典型) | 一个 tile 必须 ≤ L1 大小 |
| L2 cache | 256KB-1MB | 可容纳多字段或相邻 tile，但不是第一目标 |
| 每个 double 宽度 | 8 字节 | 决定了 tile 行列数的乘积上限 |
| 64 字节 cache line | 恰好 8 doubles | 当 stride 对齐时无内部碎片 |
| 建议 tile 大小 | 64×64 = 4096 doubles | 满足 ≤ 32KB L1，且两个维度相等避免偏移偏好 |

若字段数很多（如 8 个 OHLCV 字段），处理字段 k 时只需 tile 中该字段的部分（32KB），后续字段按需装入。这比 8 字段混排（256KB tile，必然不命中 L1）要好。

### 时序访问（stride=1）

```
遍历 S_1 的所有日期:
  v[0], v[1], ..., v[63]  → 均在 tile 的第一行
  stride = 1 (相邻 double)
  
  cache line 0: v[0..7]   → 第一次访问 miss，后续 7 个全 hit
  cache line 1: v[8..15]  → 硬件预取器已提前加载
  cache line 2: v[16..23] → 同上
  ...
  
  有效利用率: 100%（每个 cache line 的 8 个 double 全被使用）
  预取器: 完美预测（线性递增地址）
```

结论：时序访问仍然是 **stride=1，100% 带宽利用率**，与 `MarketData` 的 `Column<T>` 相比没有退化。

### 截面访问（stride=64）

```
遍历 D_k 列（64 只股票在同一日期的值）:
  v[k], v[64+k], v[128+k], ..., v[4032+k]
  stride = 64 doubles = 512 字节 = 8 条 cache line
  
  第一次: v[k]        → L1 miss，但触发 cache line 填充
                      → 同一 cache line 内 v[k+1..k+7] 被顺带装入（虽然本次不需要）
  第二次: v[64+k]     → L1 hit！（因为整个 32KB tile 已经在前几次访问中逐步装入 L1）
  第三次: v[128+k]    → L1 hit
  ...
```

关键点：**stride 本身不是问题——问题在于工作集能否装入 cache**。

```
无分块时：工作集 = 1000 只股票散落在 GB 级内存中，cache 永远装不下
有分块时：工作集 = 32KB 的 tile，整个在 L1 cache 内
```

| 指标 | 无分块（跨 MarketData gather） | 有分块（tile-based） |
|------|-------------------------------|---------------------|
| 每次访问延迟 | ~200 cycles (DRAM) | ~4 cycles (L1 hit) |
| 单 tile 内 64 次截面访问 | 64 × 200 = 12,800 cycles | ~16 cycles（4×4 首次 miss） |
| 1000 只股票全截面 | 200,000 cycles | ~3,200 cycles（16 tiles × 200 cycles/tile miss） |
| Cache line 有效利用率 | 12.5% (时序 100%) | 时序 100%, 截面 12.5% 但无 DRAM 代价 |
| TLB miss | ~1000 次 | ~8 次/tile（32KB = 8 个 4KB 页） |
| 硬件预取 | 无效（不可预测跳转） | 有效（stride=512 是规律模式，可被 stride prefetcher 识别） |

## 四、内存开销量化

### 4.1 数据本身：零额外开销

```
分块前：N_stocks × N_dates × sizeof(double) = N × M × 8
分块后：N_stocks × N_dates × sizeof(double) = N × M × 8  （相同）
```

同一个二维矩阵，只是元素的排列顺序改变——类似行优先 vs 列优先的差别，不增不减。

### 4.2 对齐填充：~2-5%

当 N_stocks 或 N_dates 不能被 64（tile 大小）整除时，末尾 tile 的部分行/列需要填充：

```
N_stocks = 1000 → 1000 / 64 = 15.625 → 16 个 tile-stripe
最后一个 stripe 利用率 = 1000 - 15×64 = 40 / 64 = 62.5%
该 stripe 的每行浪费 24×8 = 192 字节

单字段浪费 = 24 stocks × 1000 dates × 8B ≈ 192KB
单字段总量 = 1000 × 1000 × 8B = 8MB
浪费比例 = 192KB / 8MB ≈ 2.3%
```

对于全部 7 个 OHLCV 字段：
- 总数据量：7 × 8MB = 56MB
- 总填充浪费：7 × 192KB ≈ 1.3MB
- 浪费比例：~2.3%

| N_stocks | N_dates | 总数据 | 填充浪费 | 比例 |
|----------|---------|--------|---------|------|
| 5000 | 2500 | 100MB | ~3.2MB | 3.2% |
| 5000 | 5000 | 200MB | ~4.8MB | 2.4% |
| 10000 | 5000 | 400MB | ~18MB | 4.5% |
| 20000 | 5000 | 800MB | ~37MB | 4.6% |

**结论**：A 股市场约 5000 只股票时，填充开销约为 2-3%。即便是极端场景也始终 ≤ 5%。

### 4.3 索引结构：可忽略

```cpp
class PanelData {
    // 每个 tile 的元数据
    // 总 tile 数 = ceil(N_stocks/64) × ceil(N_dates/64)
    // 5000 stocks × 2500 dates → (79 × 40) = 3,160 tiles
    struct TileMeta {
        size_t dataOffset;   // 8 字节
        uint32_t stockStart; // 4 字节
        uint32_t dateStart;  // 4 字节
        uint16_t nStocks;    // 2 字节（边界 tile 可能 < 64）
        uint16_t nDates;     // 2 字节
    };  // 20 字节/tile → 3,160 × 20 ≈ 63KB
    
    // stock_idx → 首 tile 的映射（用于时序访问快速定位）
    // 5000 × 4 bytes = 20KB
    
    // date_idx → tile 行的映射（用于截面访问快速定位）
    // 2500 × 4 bytes = 10KB
};
```

总索引开销 < 100KB，远小于数据本身（百 MB 级）。

### 4.4 截面物化缓冲区：临时开销

截面求值时需要一个连续 buffer 来收集结果，之后立即归还：

```cpp
// 临时从 BufferPool 分配
auto buf = pool.allocate<double>(assetCount());  // N_stocks × 8B
// 5000 stocks = 40KB
// 求值结束后 buf 析构，内存归还池
```

| 资产数 | 缓冲大小 | 生命周期 |
|--------|---------|---------|
| 5000 只 | 40KB | 一次截面求值调用 |
| 10000 只 | 80KB | 同上 |
| 20000 只 | 160KB | 同上 |

不是持久开销，且通过 `BufferPool` 复用，实际内存占用接近于零。

### 4.5 总开销汇总

| 项目 | 大小 (5000 stocks × 2500 dates) | 性质 |
|------|--------------------------------|------|
| 数据本身 | 7 fields × 8B × 12.5M = 700MB | 必须 |
| 对齐填充 | ~22MB (~3%) | 持久，不可避免 |
| 索引结构 | ~100KB | 持久，可忽略 |
| 截面物化缓冲 | 40KB/调用 | 临时，BufferPool 复用 |
| **总计** | ~722MB | 纯数据 700MB + 开销 ~22MB |

## 五、对比：要不要保留双份存储

| 方案 | 存储占用 | 时序性能 | 截面性能 | 维护复杂度 |
|------|---------|---------|---------|-----------|
| A. 仅 MarketData（当前） | 700MB | stride=1 最优 | cache miss 200k cycles | 低 |
| B. MarketData + 分块双份 | ~1.4GB | 均可最优 | 均可最优 | 高（同步两份） |
| C. 仅分块存储 | ~722MB | stride=1 最优 | L1 hit 4 cycles | 中（tile 索引） |

**推荐方案 C**：仅维护分块存储。分块布局也能产出 `MarketData` / `ColView<T>` 供时序方向使用（沿行切片即可），所以不需要双份。额外的 22MB 对齐填充（~3%）换来了截面方向 50x+ 的性能提升，是极好的 trade-off。

---

## 六、核心结论

1. **分块不靠消除 stride，靠缩小工作集**。截面 stride=64 不是问题——问题是 1000 只股票散落在 GB 级内存中无法装入 cache。一个 32KB tile 装入 L1 后，stride=64 的延迟从 200 cycles 降到 4 cycles。

2. **时序访问无退化**。分块的行内仍是 stride=1，与 `Column<T>` 的连续内存完全相同。硬件预取器正常工作，带宽利用率 100%。

3. **额外内存开销约 3%**。来自未对齐 tile 的填充，加上约 100KB 的索引元数据。没有实质性成本。

4. **不需要双份存储**。分块布局对两个方向都能高效访问，不需要同时保留 `MarketData` 布局。
